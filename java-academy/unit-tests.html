Lesson 17 · Advanced Java

Unit Tests: Setup & Run in Android Studio

A hands-on guide to automated testing in Android Studio: add JUnit to a plain Java module and to an Android app, write your first tests, run them every way the IDE and Gradle allow, read the results and reports, measure coverage, mock dependencies, and run everything automatically on every push.

⏱ 50 min🎯 Advanced🧩 Prerequisite: lessons 01 and 16

You will be able to

  • Set up JUnit 5 in a Java module and JUnit 4 in an app module
  • Create tests with Ctrl+Shift+T
  • Run one test, a class, a package or everything
  • Run tests with Gradle and read the HTML reports
  • Measure code coverage and mock with Mockito
  • Run tests in CI and fix the usual setup errors

17.1Which tests, where?

Think of tests as a pyramid: many fast unit tests at the bottom, fewer slower integration tests, and a handful of end-to-end UI tests at the top. In an Android Studio project they live in two different source sets:

This lesson focuses on local unit tests — the ones you'll write and run dozens of times a day. Lesson 22 goes deeper into instrumented and UI tests.

The Run tool window shows a tree of results: ✔ green for passed, ✘ red for failed, with the time each test took. Click a failed test to see its message and stack trace; for assertEquals failures, <Click to see difference> opens a side-by-side diff of expected vs actual.

Pin the test configuration (toolbar dropdown → it's saved automatically) and run it after every small change. Toggle Toggle auto-test in the Run window to re-run tests automatically whenever you edit code.

17.5Run tests with Gradle and read the report

🧱
“Method … not mocked”

Local tests compile against a stub android.jar whose methods throw RuntimeException("Method ... not mocked"). The real fix is architectural: keep logic in plain Java classes (Spendly's whole domain package has no Android imports) so it's trivially testable. isReturnDefaultValues = true softens the stubs; Robolectric simulates the framework if you truly need it; otherwise write an instrumented test.

Testing a ViewModel that uses LiveData? Add InstantTaskExecutorRule so LiveData runs synchronously on the test thread — exactly what Spendly's ExpenseListViewModelTest does (lesson 23):

Want JUnit 5 in an Android module too? Android Gradle Plugin doesn't run it natively; the community plugin de.mannodermaus.android-junit5 adds support. Most Android teams stay on JUnit 4 for app modules and use JUnit 5 in pure Java/Kotlin modules.

17.7Code coverage

Coverage shows which lines your tests executed. It finds untested code — it does not prove the tests check the right things.

  • In the IDE: gutter ▶ → Run 'PriceCalculatorTest' with Coverage. The Coverage tool window lists % of classes, methods and lines; the editor marks lines green (covered), red (missed) or yellow (partially, e.g. one branch of an if).
  • With Gradle (Java module): apply the jacoco plugin and run ./gradlew :lessons:test :lessons:jacocoTestReport; open lessons/build/reports/jacoco/test/html/index.html.
  • With Gradle (Android module): enable it for the debug build type and run ./gradlew :app:createDebugUnitTestCoverageReport; the report lands in app/build/reports/coverage/test/debug/.
lessons/build.gradle.kts
app/build.gradle.kts

Aim for high coverage of domain logic (rules, calculations, parsing); don't chase 100 % on Activities and generated code.

17.8Mocking with Mockito

When the class under test talks to something slow or external (network, clock, database), replace it in the test. Lesson 16 showed hand-written fakes; Mockito creates stand-ins on the fly and lets you verify interactions:

Add testImplementation("org.mockito:mockito-core:5.14.2"). Prefer fakes for data you control; reach for mocks when you need to assert “this call happened” or to simulate rare failures. Don't mock types you don't own (like Context) — wrap them behind your own interface instead.

17.10Red → Green → Refactor

Test-driven development flips the order: write a failing test first, then the simplest code that passes, then clean up. It forces small steps and testable designs.

🔴 Redwrite a failing test
→
🟢 Greensimplest code that passes
→
🔵 Refactorclean up, tests stay green
↺
  1. Test: assertEquals("1", FizzBuzz.of(1)); — doesn't even compile → create FizzBuzz.of returning "" → red.
  2. Make it pass: return String.valueOf(n); → green.
  3. Next test: assertEquals("Fizz", FizzBuzz.of(3)); → red → add the rule → green.
  4. Continue with 5 → "Buzz", 15 → "FizzBuzz"; refactor with a parameterised test once the cases form a table.
