Final Project: Spendly — a complete Android app in Java

Everything comes together. Over nine milestones you'll build Spendly, a production-style expense tracker: Material 3 screens, ViewModel + LiveData, a Room database, settings, live exchange rates, daily reminders with WorkManager, and automated tests — all in Java. Every file below is the real source that CI builds and tests on every push.

⏱ ~6 hours🎯 Master🧩 Prerequisite: lessons 01–22📦 final-project/Spendly

You will build

  • A monthly overview with totals and a category breakdown
  • Search, category filters and swipe-to-delete with Undo
  • A validated editor with a date picker
  • Settings: currency, theme, daily reminder
  • Currency conversion over HTTP
  • Unit, database and UI tests running in CI

23.4The domain model

Milestone 2 — The domain model

Goal: plain Java types for expenses, money and the rules of the app — no Android code at all.

Expense is a record whose compact constructor validates and normalises input. Money is stored as cents in a long; Money parses user input with BigDecimal and formats with NumberFormat. ExpenseFilter, MonthlySummary and ExpenseListState are immutable values built by pure functions. ExpenseValidator reports problems as enums so the UI can localise the messages. Notice the API choices: trim() instead of strip(), Collectors.toList() instead of Stream.toList() — required for minSdk 26 (lesson 18).

23.5Persist expenses with Room

Milestone 3 — Persist expenses with Room

Goal: an expenses table, a DAO that exposes LiveData, and mappers between rows and records.

The entity keeps storage-friendly primitives: the category as its name() and the date as an epoch day, which sorts numerically. @Upsert both inserts new rows and restores deleted ones — that's how Undo works. The mapper is the only place that knows both worlds.

23.6Repositories, settings & network

Milestone 4 — Repositories, settings & network

Goal: the data layer the ViewModels will talk to.

ExpenseRepository is an interface; RoomExpenseRepository maps LiveData from the DAO and performs writes on an injected Executor. SettingsStore wraps SharedPreferences and publishes changes as LiveData. The exchange-rate service uses HttpURLConnection and parses JSON with Gson's tree model, translating every failure into an IOException.

23.8The list screen

Milestone 6 — The list screen

Goal: month navigation, a summary card, category chips, search, the list, swipe-to-delete with Undo and currency conversion.

ExpenseListViewModel combines three inputs (all expenses, month, filter) with a MediatorLiveData into one ExpenseListState. The Activity only renders state and forwards events. ExpenseAdapter is a ListAdapter whose DiffUtil callback relies on record equality. SystemBars handles edge-to-edge insets.

23.9Editor, settings & resources

Milestone 7 — Editor, settings & resources

Goal: create and edit expenses with validation, and a settings screen.

The edit ViewModel loads an existing expense once, keeps the selected category and date, and delegates validation to the domain. The Activity maps each validation Problem to a string, reattaches the date picker listener after rotation, and avoids overwriting the user's typing when the ViewModel re-delivers data. Settings uses exposed-dropdown menus, radio buttons and a switch that requests the notification permission on Android 13+.

23.10Daily reminders with WorkManager

Milestone 8 — Daily reminders with WorkManager

Goal: at 20:00, if nothing was logged today, a notification appears — even if the app is closed.

The scheduling maths lives in ReminderTime, a pure function with unit tests. ReminderScheduler enqueues unique periodic work so toggling the switch never stacks duplicates. The worker queries Room directly on its background thread, and Notifications checks the runtime permission before posting.

23.11Tests, CI & release

Milestone 9 — Tests, CI & release

Goal: automated proof that Spendly works, on every push, plus a release configuration.

JVM tests drive the ViewModel through in-memory fakes and a fixed Clock; instrumented tests exercise the real Room database and the UI with Espresso. The GitHub Actions workflow builds the APK, runs unit tests, compiles instrumented tests and runs Lint (which would catch any API newer than minSdk). R8 shrinks the release build.
