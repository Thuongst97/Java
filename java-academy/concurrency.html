Lesson 15 · Advanced Java

Concurrency

On Android, one thread draws the UI; anything slow must happen elsewhere or the app freezes. On servers, thousands of requests run at once. Learn threads, the bugs they cause, and the high-level tools — executors, atomics, concurrent collections, CompletableFuture and virtual threads — that make concurrency manageable.

⏱ 75 min🎯 Advanced🧩 Prerequisite: lesson 13

You will be able to

  • Start and join threads
  • Explain and fix race conditions
  • Use synchronized, atomics and volatile
  • Run tasks on an ExecutorService
  • Compose async work with CompletableFuture
  • Apply the main-thread rules of Android

15.1Threads

A thread is an independent path of execution inside your program; all threads share the same heap. You give a thread a Runnable and call start() (not run(), which would just execute it on the current thread). join() waits for it to finish.

The order of lines between the threads is not deterministic — the OS scheduler decides. Only the last line is guaranteed to come last, thanks to join().

15.2Race conditions and how to fix them

count++ looks atomic but is three steps: read, add, write. When two threads interleave those steps, updates are lost. That's a race condition.

🔒
Deadlock

Thread 1 holds lock A and waits for B; thread 2 holds B and waits for A — both wait forever. Avoid it by always acquiring locks in the same order, keeping synchronized blocks tiny, and never calling unknown code (callbacks) while holding a lock.

15.3Executors: thread pools done right

Creating a thread per task is expensive and unbounded. An ExecutorService manages a pool of reusable threads; you submit tasks and get back Futures for their results.

Four 50 ms tasks finish in about 50 ms because four pool threads run them at the same time. Future.get() rethrows a task's exception wrapped in ExecutionException.

15.5CompletableFuture: composing async work

Future.get() blocks. CompletableFuture lets you describe what happens when a result arrives — transform it, combine two results, recover from errors — without blocking a thread while you wait.

15.6Virtual threads (Java 21)

Platform threads are expensive (≈1 MB of stack each), so servers used to need complex async code. Virtual threads are lightweight threads managed by the JVM: you can run a million of them, writing simple blocking code.

🤖
Not on Android

Virtual threads are a JDK 21 feature for server and desktop JVMs. Android's runtime doesn't provide them; on Android use a small fixed pool (Executors.newFixedThreadPool), WorkManager for deferrable work, or Kotlin coroutines in Kotlin code.

15.7Concurrency on Android

  • Block the main thread for ~5 seconds and Android shows “App isn't responding” (ANR). Network on the main thread throws NetworkOnMainThreadException immediately.
  • Updating a View from a background thread throws CalledFromWrongThreadException.
  • The modern Java pattern: a background ExecutorService in your repository, results delivered with LiveData.postValue() (lesson 20), which the UI observes on the main thread.
  • AsyncTask is deprecated — don't use it. For work that must survive the app closing (sync, reminders), use WorkManager (lesson 21).

15.8Exercises

Exercise 1 — Parallel sum Easy

Sum the numbers 1…10,000,000 by splitting the range into 4 chunks, each summed by a Callable on a fixed pool of 4 threads.

Exercise 2 — A thread-safe bank account Medium

Make withdraw safe so that 100 concurrent withdrawals of 10 from a balance of 500 succeed exactly 50 times and the balance never goes negative. Why isn't an AtomicLong with separate get and addAndGet calls enough?

Separate atomic calls leave a gap between the check and the update in which another thread can withdraw. (A compareAndSet loop on an AtomicLong also works.)

Exercise 3 — Fastest mirror Challenge

Three “mirrors” return the same file after 120, 40 and 80 ms. Use CompletableFuture.anyOf to take the first result, and add a timeout fallback with completeOnTimeout.
