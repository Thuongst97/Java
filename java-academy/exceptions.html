Lesson 10 · Object-Oriented Java

Exceptions, Null & Optional

Things go wrong: files are missing, networks drop, users type nonsense. Learn to read stack traces, handle and throw exceptions properly, manage resources with try-with-resources, and tame null — the most common crash on Android.

⏱ 50 min🎯 Intermediate🧩 Prerequisite: lesson 08

You will be able to

  • Read a stack trace and find the bug
  • Distinguish checked and unchecked exceptions
  • Use try/catch/finally and multi-catch
  • Close resources with try-with-resources
  • Design custom exceptions
  • Avoid NullPointerException and use Optional well

10.1What an exception is — and how to read a stack trace

An exception is an object that describes an abnormal event. When one is thrown, normal execution stops and the JVM unwinds the call stack looking for a matching catch. If none is found, the thread dies and prints a stack trace:

  1. First line: the exception type (ArithmeticException) and message (/ by zero) — what happened.
  2. Top frame: where it was thrown — Crash.java line 3.
  3. Frames below: who called whom. Read downward until you reach your code that made the wrong decision — here line 14 passes an empty array.
🤖
On Android

An uncaught exception shows the “App keeps stopping” dialog, and the trace appears in Logcat (filter by level Error or search FATAL EXCEPTION). Click the blue File.java:line links to jump to the code. Long traces have Caused by: sections — the last one is usually the root cause.

10.3try, catch and finally

  • Catch blocks are tried in order; put subclasses before superclasses (NumberFormatException extends IllegalArgumentException — reversing them is a compile error).
  • finally runs whether the block completes, returns or throws — historically used to release resources (see next section for the better way).
  • Never return from finally: it silently discards any exception in flight.

10.4throw and throws

throw raises an exception. A method that may let a checked exception escape must declare it with throws, and its callers must handle it in turn.

10.5try-with-resources

Files, sockets, database cursors and streams must be closed, even when an error occurs. Declare them in try ( … ) and Java closes them automatically, in reverse order, for any class that implements AutoCloseable.

If close() itself throws while another exception is in flight, the second one is attached as a suppressed exception (e.getSuppressed()) instead of hiding the first. On Android you'll use this for Cursor, InputStream and HttpURLConnection streams.

10.6Custom exceptions and wrapping causes

Create your own exception type when callers need to react to a specific failure. When you translate a low-level exception into a higher-level one, pass the original as the cause so the stack trace keeps the full story.

10.7Exception best practices

  • Fail fast: validate arguments at the start of public methods — Objects.requireNonNull(x, "x"), IllegalArgumentException for bad values, IllegalStateException for calls at the wrong time.
  • Never swallow: an empty catch (Exception e) {} hides bugs forever. At minimum log it (Log.e(TAG, "msg", e) on Android).
  • Catch specific types, as close as possible to where you can actually do something useful.
  • Don't use exceptions for control flow — check list.isEmpty() instead of catching NoSuchElementException.
  • Keep causes when wrapping: new XException("context", e).
  • Don't catch Error (or Throwable) unless you're writing a framework.

10.8null and NullPointerException

Calling a method or reading a field through a null reference throws NullPointerException (NPE). Since Java 14, “helpful NPE” messages tell you exactly which part was null:

Defences, from best to worst

  1. Don't produce null: return empty collections (List.of()) and empty strings; use Optional for “maybe a value” return types.
  2. Reject null at the boundary: this.name = Objects.requireNonNull(name, "name"); — the error appears where the bug is, not 200 lines later.
  3. Annotate: on Android use @NonNull / @Nullable from androidx.annotation. Android Studio then warns when you dereference something nullable — and Kotlin callers see real nullable types.
  4. Provide defaults: Objects.requireNonNullElse(value, "unknown").
  5. Check explicitly (if (x != null)) where null is a legitimate state.

10.9Optional: an explicit “maybe”

Optional<T> is a box that is either empty or contains a non-null value. Returning one makes absence part of the method's type, so callers can't forget to handle it.

🧭
Use Optional for return values only

Don't use it for fields, method parameters or collections (return an empty list instead). Never call get() without checking — use orElse, orElseGet, orElseThrow, map and ifPresent. And never return null from a method whose return type is Optional!

10.10Exercises

Exercise 1 — Robust number input Easy

Read lines until the user enters a valid whole number, printing “Try again” for invalid input. Use Integer.parseInt and catch NumberFormatException.

Exercise 2 — Validated constructor Medium

Write record Email(String value) whose compact constructor rejects null (NullPointerException via requireNonNull) and values without exactly one @ (IllegalArgumentException), and lower-cases valid addresses.

Exercise 3 — Retry with backoff Challenge

A flaky operation fails twice with IOException then succeeds. Write retry(int maxAttempts, Callable<T> op) that retries on IOException only, doubling a (simulated) delay each time, and rethrows the last failure if all attempts fail.

Retry::flaky is a method reference and <T> makes the method generic — both explained in lessons 11 and 13.
