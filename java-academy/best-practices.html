Java Coding Rules & Best Practices

Code is read far more often than it's written. These are the rules professional Java and Android teams follow — each shown as a ✗ Avoid / ✓ Prefer pair with the reason behind it. Use this page as a checklist while you write and review code.

⏱ 60 min🎯 All levels🧩 Builds on lessons 03–22

You will be able to

  • Format and name code the way every Java team expects
  • Write small, focused methods and classes
  • Handle null, errors and resources safely
  • Use collections, streams and threads without traps
  • Apply Android-specific rules
  • Refactor messy code step by step
📏
Where these rules come from

The Google Java Style Guide, the Android code style, Joshua Bloch's Effective Java, and the inspections built into Android Studio. When your team has its own style guide, it wins — consistency matters more than any single rule.

B.1Formatting and layout

  • Let the IDE format: Ctrl+Alt+L (⌘+⌥+L), and enable Settings → Tools → Actions on Save → Reformat code + Optimize imports. Never argue about spaces in code review.
  • Always use braces, even for one-line if/for bodies.
  • One statement per line, one variable per declaration.
  • Keep lines ≤ 100 characters; break long call chains one call per line.
  • No wildcard imports (import java.util.*;) — explicit imports show exactly what a file depends on.
  • Order members: constants, fields, constructors, public methods, private helpers — so readers know where to look.

✓ Prefer

The rule behind the rules

A name should make a comment unnecessary. If you need // number of days until the bill is due next to int d, rename it. Avoid abbreviations (mgr, cnt), Hungarian prefixes (strName, mName in new code) and meaningless suffixes (Manager, Helper, Data) when a precise word exists. Rename safely with Shift+F6.

B.3Variables and constants

  • Declare variables in the smallest scope, right where they're first used.
  • Make them final when they never change — especially fields. Immutability removes a whole class of bugs.
  • No magic numbers or strings: give them a named constant.
  • Use var only when the type is obvious from the right-hand side.
  • Never use double for money — use long cents or BigDecimal.

B.4Methods

  • One method, one job, at one level of abstraction. If you can describe it with “and”, split it.
  • Short: most methods fit on one screen (≈ 20 lines). Use Extract Method (Ctrl+Alt+M).
  • Few parameters (≤ 3–4). More → a record or a builder.
  • Guard clauses: handle invalid cases first and return early instead of nesting.
  • No boolean flag parameters — render(true) means nothing at the call site; make two methods.
  • Validate arguments of public methods and fail fast.
  • Return values instead of printing or mutating parameters (pure functions are easy to test).
✗ Avoid: arrow code
✓ Prefer: guard clauses
✗ Avoid: flags & long parameter lists
✓ Prefer: named types & methods

B.5Classes and objects

  • Fields private, expose behaviour rather than raw state; don't generate setters by reflex.
  • Prefer immutable types: records for data, final fields, “wither” methods for changes.
  • Favour composition over inheritance; make classes final unless designed for extension.
  • Program to interfaces (List, ExpenseRepository) and receive dependencies in the constructor.
  • Static factory methods (Money.ofCents(…)) or a builder when constructors get confusing.
  • Override equals and hashCode together (or use a record), and add @Override everywhere.
  • Never call overridable methods from a constructor.
✗ Avoid: a mutable bag of fields
✓ Prefer: a validated value

B.7Null and Optional

  • Don't return null for collections — return an empty one.
  • Use Optional only as a return type for “maybe absent”; never for fields or parameters, never call get() blindly.
  • Reject null at the boundary with Objects.requireNonNull(x, "x").
  • Annotate with @NonNull/@Nullable (androidx.annotation) so the IDE warns you.
✗ Avoid
✓ Prefer

B.8Exceptions and resources

  • Never swallow exceptions — at least log them with the exception object.
  • Catch the most specific type, where you can actually handle it; never catch Throwable or Error.
  • Keep the cause when wrapping: new RepositoryException("…", e).
  • Unchecked for programming errors (IllegalArgumentException, IllegalStateException), checked for recoverable conditions.
  • Close resources with try-with-resources, never in a hand-written finally.
  • Don't use exceptions for control flow, and don't return from finally.
✗ Avoid
✓ Prefer

B.9Collections, strings and streams

  • Declare with interfaces: List<Expense> items = new ArrayList<>();
  • Return immutable collections or defensive copies from your classes.
  • Don't modify a collection while iterating it — use removeIf or an Iterator.
  • Use StringBuilder (or String.join/Collectors.joining) when building strings in loops.
  • Streams without side effects; collect results instead of adding to outside lists. Prefer a loop when it's clearer.
  • Use the modern Map API: getOrDefault, merge, computeIfAbsent.
✗ Avoid
✓ Prefer

B.10Concurrency

  • Share immutable objects; when you must share mutable state, guard every access with the same lock or use atomics/concurrent collections.
  • Use executors, not new Thread() — and always shut them down.
  • Keep synchronized blocks tiny and never call unknown code (callbacks, I/O) while holding a lock.
  • Never use Thread.sleep to “wait until it's ready” — use join, Future, CountDownLatch or callbacks.
  • Don't swallow InterruptedException: restore the flag with Thread.currentThread().interrupt().
✗ Avoid
✓ Prefer

B.11Comments and Javadoc

  • Explain why, not what — the code already says what.
  • Javadoc every public API: purpose, parameters, return value, exceptions, edge cases.
  • Delete commented-out code; git remembers it.
  • Turn comments into names when you can (extract a well-named method or variable).
  • TODOs need context: // TODO(ada): remove after API v2 ships (#123).
✗ Avoid
✓ Prefer

The code-review checklist

  • Does every name say what it is or does?
  • Is each method short and doing one thing? Any flag parameters or long parameter lists?
  • Are fields private and final where possible? Could this be a record?
  • Any == on objects, money in double, magic numbers?
  • Can anything be null that isn't handled? Any returned null collections?
  • Are exceptions specific, logged, never swallowed? Are resources closed?
  • Is shared state thread-safe? Is anything slow running on the Android main thread?
  • Are there tests for the new behaviour, and do they pass in CI?
