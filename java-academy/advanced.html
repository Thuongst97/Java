16.1Unit testing with JUnit 5

A unit test is code that calls your code and checks the result. Run them on every change and you'll catch regressions in seconds, not in production. Add JUnit 5 to the lessons module:

JUnit 4 on Android

Android app modules still use JUnit 4 by default (@Test from org.junit, @Before instead of @BeforeEach, @Rules). The ideas are identical — the final project's tests use JUnit 4 so they work with AndroidX test rules. Lesson 22 covers instrumented and UI tests.

16.2Designing for testability: fakes

Code that reaches out to the clock, the network or a database directly is hard to test. Depend on an interface, receive it through the constructor, and in tests pass a fake — a tiny, controllable implementation.

🎭
Fakes vs mocks

A fake is a real, simple implementation (an in-memory repository). A mock (Mockito: mock(Notifier.class), verify(notifier).send("…")) records calls and lets you assert on them. Prefer fakes for data and state; reach for mocks when you need to verify an interaction with something you don't own.

16.3Annotations and reflection

An annotation attaches metadata to code (@Override, @Test, Room's @Entity). Some are read by the compiler or annotation processors at build time; those with RetentionPolicy.RUNTIME can be read while the program runs through reflection — the API for inspecting classes, methods and fields dynamically. Reflection on Android

Reflection is slow-ish and bypasses compile-time checks. On Android, release builds are shrunk and obfuscated by R8, which renames or removes classes it thinks are unused — breaking code that finds them by name. That's why libraries like Room and Hilt generate code at build time with annotation processors instead, and why reflection-based libraries (e.g. Gson) need -keep rules (lesson 22).

16.4Inside the JVM: memory, GC and the JIT

Stack

One per thread. Holds a frame per active method call with its local variables and parameters (primitives and references). Freed automatically on return. Too deep → StackOverflowError.

Heap

Shared by all threads. Every object and array lives here. Reclaimed by the garbage collector when unreachable. Too full → OutOfMemoryError.

Metaspace

Class metadata: methods, bytecode, constant pools. Grows as classes are loaded.

  • Generational GC: most objects die young, so the heap has a young generation collected often and cheaply, and an old generation collected rarely. Modern collectors (G1, ZGC) pause your program for only milliseconds.
  • JIT: the JVM interprets bytecode, profiles it, and compiles hot methods to optimised machine code — inlining calls and removing allocations. That's why Java benchmarks need a warm-up.
  • ART on Android combines ahead-of-time compilation (at install / with Baseline Profiles), a JIT and a concurrent copying GC. Each app has a heap limit (often 256–512 MB) — leaks hit it fast.
  • Memory leaks in Java are objects still reachable but no longer needed: static references to Activities, listeners never unregistered, unbounded caches. Find them with Android Studio's Memory Profiler (heap dumps) and LeakCanary.

The simplest correct singleton of all is an enum with one constant: enum Settings { INSTANCE; … }. In Android apps, prefer creating one instance in your Application class and passing it where needed (dependency injection) over global singletons — it keeps code testable.

16.6The code-review checklist

  • Names say what things are and methods say what they do; no abbreviations a newcomer can't decode.
  • Classes are small, focused and immutable where possible; fields are private final by default.
  • Public methods validate arguments; nothing returns null where an empty collection or Optional would do.
  • equals/hashCode are overridden together (or the type is a record).
  • Exceptions are specific, never swallowed, and keep their cause.
  • Resources are closed with try-with-resources; threads and executors are shut down.
  • Shared mutable state is avoided or properly synchronised.
  • Dependencies are passed in (interfaces), so every class can be unit-tested with fakes.
  • Behaviour is covered by fast unit tests that run on every change.

16.7Exercises

Exercise 1 — Test a validator Easy

Write isStrongPassword(String) (≥ 8 chars, a digit, an upper-case letter) and a table of test cases checked in main, printing PASS/FAIL like a parameterised test.

Exercise 2 — An event bus Medium

Build a type-safe event bus: <T> void subscribe(Class<T> type, Consumer<T> handler) and void publish(Object event) that delivers only to handlers registered for the event's class.

Exercise 3 — A tiny dependency container Challenge

Write a Container with <T> void singleton(Class<T> type, Supplier<T> factory) and <T> T get(Class<T> type) that creates each object lazily, once. This is what Hilt/Dagger generate for you — and what Spendly's AppContainer does by hand.
