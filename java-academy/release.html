Lesson 22 · Android with Java

Testing, Debugging & Publishing

The last mile: prove the app works on real devices with instrumented and UI tests, hunt bugs with Android Studio's debugger and inspectors, then shrink, sign and ship an App Bundle to Google Play.

⏱ 50 min🎯 Master🧩 Prerequisite: lessons 17, 20–21

You will be able to

  • Write instrumented and Espresso UI tests
  • Debug with breakpoints, Logcat and inspectors
  • Find performance problems and memory leaks
  • Configure R8 and read obfuscated stack traces
  • Sign a release build without leaking secrets
  • Publish an App Bundle through Play's testing tracks

22.1Instrumented and UI tests

Lesson 17 covered JVM unit tests. Instrumented tests live in src/androidTest and run on an emulator or phone with the real framework. Start a device, then click the gutter ▶ or run ./gradlew connectedDebugAndroidTest; the report lands in app/build/reports/androidTests/connected/.

Espresso: UI tests

Espresso finds views, performs actions and checks results — and waits automatically until the UI is idle. The pattern is always onView(matcher).perform(action).check(assertion):

Turn off animations on test devices (Developer options → window/transition/animator scale = off) to avoid flakiness. Android Studio's Espresso Test Recorder (Run → Record Espresso Test) can generate a first draft.

A debugging routine that works

1. Reproduce reliably. 2. Read the whole stack trace — the first line of your code is where to look. 3. Form a hypothesis and test it with a breakpoint, not with guesses. 4. Write a failing test for the bug, then fix it so it never returns.

22.3Performance and memory

  • Profiler (View → Tool Windows → Profiler): CPU traces show which methods are slow; the memory profiler shows allocations and lets you capture heap dumps.
  • StrictMode in debug builds flags disk and network access on the main thread:
  • LeakCanary (debugImplementation("com.squareup.leakcanary:leakcanary-android:…")) detects leaked Activities automatically and shows the reference chain — usually a static field, a listener or an inner class (lessons 09 and 20).
  • Smooth lists: keep onBindViewHolder cheap, use ListAdapter, avoid nested weights and deep layouts.

22.4R8: shrinking, optimising and obfuscating

Release builds run R8: it removes unused classes and methods (including from libraries), optimises bytecode, renames identifiers to short names, and with isShrinkResources drops unused resources. APKs often shrink by half.

Obfuscated crashes look like at a.b.c(SourceFile:12). R8 writes a mapping file (app/build/outputs/mapping/release/mapping.txt); keep it for every release. Google Play deobfuscates automatically when you upload it, or use retrace from the command line. Always test the release build before shipping — R8 problems only appear there.

22.5Signing a release

Every APK/AAB must be signed. Debug builds use an automatic debug key; releases need your own upload key. With Play App Signing (the default), Google holds the final app signing key and you sign uploads with an upload key that can be reset if lost.

  1. Create a keystoreBuild → Generate Signed App Bundle or APK → Android App Bundle → Create new…. Store the .jks file outside the repository and back it up.
  2. Keep secrets out of gitPut paths and passwords in keystore.properties (listed in .gitignore) and read them in Gradle — exactly what Spendly's build script does. In CI, provide them as encrypted secrets.
  3. Build./gradlew bundleRelease → app/build/outputs/bundle/release/app-release.aab.

22.6Publishing on Google Play

  1. PrepareBump versionCode (every upload needs a higher one) and versionName; check targetSdk meets Play's current requirement; run lint, unit and instrumented tests on the release build.
  2. Play ConsoleCreate a developer account and the app; fill in the store listing (title, description, screenshots, icon), content rating questionnaire, target audience and the Data safety form (Spendly: data stays on device; it contacts an exchange-rate API).
  3. Internal testingUpload the .aab to the internal track and install it from Play on your own devices within minutes.
  4. Closed → open testingInvite testers, collect feedback and crash reports. New personal developer accounts must run a closed test with a minimum number of testers before production.
  5. Production with a staged rolloutRelease to 5–20 % of users first, watch Android vitals (crash and ANR rates), then roll out to everyone.
📦
Why App Bundles?

An .aab contains everything; Play generates optimised APKs per device (only the right screen density, CPU architecture and language), so downloads are smaller. To test exactly what users get, use bundletool or an internal testing track.

22.7Automate it

The repository's .github/workflows/android.yml builds Spendly, runs its unit tests, compiles the instrumented tests and runs Lint on every push, then uploads the reports and a debug APK. Extend it for releases: decode the keystore from a secret, run bundleRelease, and upload with the Play Developer API (e.g. the Gradle Play Publisher plugin or Fastlane).

22.8Exercises

Exercise 1 — Your first Espresso test Easy

Write a UI test for lesson 19's tip calculator: type 40, choose the 20 % chip, and check that the result text shows the expected tip and total.

Exercise 2 — Break and fix a release build Medium

Add a Gson model class mapped by reflection (no @SerializedName) to Spendly, build assembleRelease, and observe the parsed fields are null. Fix it twice: with a -keep rule and with @SerializedName. Which do you prefer and why?

Exercise 3 — Release pipeline Challenge

Extend the GitHub Actions workflow so that pushing a tag v* builds a signed bundleRelease using a base64-encoded keystore stored in repository secrets, and uploads the .aab and mapping.txt as artifacts.
