Lesson 20 · Android with Java

App Architecture: ViewModel, LiveData & Repository

An Activity that loads data, holds state, validates input and talks to the network becomes unmaintainable — and loses everything on rotation. Google's recommended architecture splits the app into layers with one job each. This lesson builds that architecture in Java, exactly as the final project uses it.

⏱ 70 min🎯 Advanced🧩 Prerequisite: lessons 15, 18–19

You will be able to

  • Separate UI, state holders and data layers
  • Keep screen state in a ViewModel that survives rotation
  • Expose and combine state with LiveData
  • Apply unidirectional data flow with immutable state
  • Design repositories as the single source of truth
  • Wire dependencies by hand or with Hilt

20.2ViewModel: state that survives rotation

A ViewModel is created the first time a screen asks for it and kept alive across configuration changes; it's cleared only when the screen is finished for good. Activities come and go — the ViewModel stays.

🚫
Never keep a View, Activity or Context in a ViewModel

The ViewModel outlives the Activity; holding the old Activity leaks it and its whole view tree. If you truly need a Context (rare), extend AndroidViewModel for the application context — or better, inject a repository that already has it.

20.3LiveData: lifecycle-aware observable state

LiveData is an observable value holder (the Observer pattern from lesson 16) that knows about lifecycles: it delivers updates only while the observer's screen is at least started, sends the latest value to new observers immediately, and removes observers automatically when the screen is destroyed — no leaks, no crashes from updating dead views.

20.4Unidirectional data flow and immutable UI state

Events flow up, state flows down. The Activity never changes what it shows directly; it asks the ViewModel, which publishes a complete new state object, which the Activity renders. Because the state is an immutable record built by a pure function, it's easy to test and impossible to half-update.

One-off events

Some outputs are events, not state: “close this screen”, “show a Snackbar”. Model them as state the UI consumes — e.g. LiveData<Boolean> finished that the edit screen observes and reacts to with finish() — or let the Activity show the Snackbar directly when it triggers the action (as Spendly does for swipe-to-delete). Avoid ad-hoc “SingleLiveEvent” hacks that lose events when no observer is active.

20.5Repositories: the single source of truth

A repository hides where data comes from (database, network, cache) behind a small interface. The rest of the app depends on the interface, so a test can pass an in-memory fake.

  • Single source of truth: the UI always reads from the database. Writes (and network refreshes) go into the database, and Room's LiveData pushes the change to every screen. No screen ever shows stale copies.
  • Offline-first: because reads come from the local database, the app works without a connection; network data is just another writer.
  • Mappers convert storage types (Room entities, JSON DTOs) to domain types, so a schema change doesn't ripple through the UI.

20.7Screens, navigation and process death

  • Multiple activities (Spendly's approach) are simple: each screen is an Activity, navigation is an Intent with extras, Back works automatically.
  • Single activity + Fragments with the Navigation component suits apps with many screens, bottom navigation or shared ViewModels. Fragments have their own lifecycle; observe LiveData with getViewLifecycleOwner().
  • Process death: in the background Android may kill your process entirely. ViewModels are gone then, but onSaveInstanceState and a ViewModel's SavedStateHandle are restored. Persist anything important (Room, preferences) immediately rather than “on exit”. Test it with Developer options → Don't keep activities or the Logcat “Terminate application” button.

20.9Exercises

Exercise 1 — Rotation-proof counter Easy

Rewrite lesson 18's counter with CounterViewModel above and remove onSaveInstanceState. Rotate: the count survives. Now enable “Don't keep activities”, press Home and return — what happens, and how would SavedStateHandle fix it?

The ViewModel dies with the process, so the count resets. Take a SavedStateHandle in the ViewModel constructor and store the count with handle.getLiveData("count", 0) — it's saved into the instance state for you.

Define NotesRepository with observeAll() and add(String), an InMemoryNotesRepository backed by a MutableLiveData<List<Note>>, and a NotesViewModel that exposes the list and a LiveData<Boolean> canAdd (input non-blank). Write two JVM tests.

Exercise 3 — Find the architecture smells Challenge

List everything wrong with this Activity and sketch the refactored ViewModel + repository:

1: static Activity reference → leak. 2: network on the main thread → crash. 3: parsing/business logic in the UI, untestable; no error handling. 4: findViewById + string concatenation for display; state (city, temperature) lost on rotation.
